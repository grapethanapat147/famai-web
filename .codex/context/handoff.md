## 0. อ่านก่อน — สถานการณ์ตอนนี้

เจ้าของงาน (เรียกว่า **เกรพ**) จะเปิดแชตใหม่พร้อมของ 3 อย่าง:

1. **ไฟล์นี้** — บริบทของระบบที่พัฒนามาในรีโป `famai-web`
2. **ซอร์สโค้ดของเพื่อนเกรพ** — อีกเวอร์ชันหนึ่งของระบบเดียวกัน คนละคนทำ
3. **สรุป feedback จากที่ประชุมกับลูกค้าล่าสุด**

**ลูกค้าเลือกใช้เวอร์ชันของเพื่อนเกรพ** ระบบในรีโปนี้จึงไม่ใช่งานส่งมอบลูกค้าแล้ว
เกรพเก็บไว้เป็นผลงานของตัวเอง และกำลังจะเอาสองเวอร์ชัน + feedback มาดูด้วยกัน

**ก่อนลงมือ ถามเกรพให้ชัดว่าต้องการอะไร** เพราะเป้าหมายเป็นไปได้หลายทางและงานต่างกันคนละเรื่อง:
- เอา feedback ลูกค้ามาใส่ในเวอร์ชันนี้ (พัฒนาต่อเป็นผลงาน)
- เทียบสองเวอร์ชันเพื่อเรียนรู้/ถอดบทเรียน
- ยกของบางส่วนจากเวอร์ชันนี้ไปใส่เวอร์ชันของเพื่อน
- ทำ portfolio / case study จากเวอร์ชันนี้

⚠️ **อย่าเดาแล้วเริ่มแก้โค้ดทันที** — ทิศทางผิดตั้งแต่ต้นเสียเวลาทั้งก้อน

## 3. กติกาการทำงานกับเกรพ (ผิดข้อไหนคือเสียเวลาทั้งคู่)

1. **เรียกว่า "เกรพ" · ตอบเป็นภาษาไทย**
2. **Ticket-first** — ทุกการเปลี่ยนแปลงต้องมีไฟล์ `.codex/tasks/tickets/FAM-XXXX.md`
   แล้วแตกสาขา `feature/FAM-XXXX-…` (หรือ `fix/` `chore/` `docs/` `style/` ตามชนิดงาน)
3. **ไม่มี `gh` CLI ในเครื่อง** — push แล้วส่ง **compare URL** ให้เกรพกด merge เองในเบราว์เซอร์
   `https://github.com/grapethanapat147/famai-web/compare/main...<branch>`
4. **PR ต้องมีคำอธิบายละเอียด** ว่าแก้อะไรบ้าง เพราะอะไร (กฎประจำของเกรพ)
5. **SQL ต้องวางเป็นข้อความในแชตเสมอ** ห้ามส่งเป็นไฟล์หรือ path — เกรพรันเองใน Supabase SQL Editor
   ส่งคำสั่งตรวจว่าเข้าไปแล้วจริง และคำสั่งย้อนกลับมาให้ด้วยทุกครั้ง
6. **ห้ามเพิ่ม dependency โดยไม่ขออนุมัติ**
7. **ห้าม commit** `.claude/` และ `supabase/config.toml` (เป็นการตั้งค่าเฉพาะเครื่อง)
8. **รัน `npx vitest run` เต็มชุดก่อน push เสมอ** — มีเทสต์หลายตัวที่ผูกข้ามไฟล์ (ดูข้อ 8)
9. GitHub เปิด auto-delete head branch แล้ว — merge เสร็จสาขาหายเอง origin เหลือ `main` อย่างเดียว

## 5. สถาปัตยกรรมที่ต้องรู้ก่อนแตะโค้ด

**RLS คือด่านจริง ไม่ใช่การกรองในแอป**
ทุกตารางเปิด RLS · helper ใน DB: `is_admin()` · `is_manager()` · `is_all_branch()` · `my_branches()` · `has_money()`
policy ผูกกับ role `authenticated` **ตัวเดียว** — ผู้ใช้ที่ล็อกอินทุกคนเป็น Postgres role เดียวกัน

**การซ่อนตัวเงินมี 2 ชั้น และต้องมีทั้งคู่**
- ชั้นแอป: `canSeeMoney()` + `stripMoneyFields()` — ตัดค่าออกฝั่งเซิร์ฟเวอร์ ไม่ส่งลง client เลย
  ตรวจแล้วว่า**ทุกหน้าที่ดึงคอลัมน์เงินมีด่านนี้ครบ**
- ชั้น DB: `has_money()` + revoke สิทธิ์คอลัมน์ + security-definer RPC
  (ทำแล้วกับ เงินเดือน/ปกส./บัญชีธนาคาร และราคาทุนของรุ่นรถ)
- **ห้ามถอดชั้นใดชั้นหนึ่ง** — DB รู้แค่สิทธิ์ตามบทบาท ไม่รู้จัก "โหมดลูกค้า" ซึ่งเป็น cookie ฝั่งแอป

**งานที่แตะเงินหรือต้องอะตอมมิก ทำใน RPC ธุรกรรมเดียว**
`sell_unit` · `sell_wholesale` · `next_doc_no` · `punch_in` / `punch_out` · `void_wholesale_order` · `next_service_reminder`

**`lib/supabase/database.types.ts` เขียนด้วยมือ**
เพิ่มคอลัมน์/ตาราง/RPC ในฐานข้อมูลแล้ว **ต้องมาเพิ่มที่ไฟล์นี้ด้วย** ไม่งั้น query จะ resolve เป็น `never`
(นี่คือ error ที่เจอบ่อยที่สุดในโปรเจกต์นี้)

**คำศัพท์ที่เจ้าของกำหนดเอง — อย่าเปลี่ยน**
- "บริษัท" ใน UI = ตาราง `branch` (FMG01 / FMM01 / FCG01) ส่วน `company` = นิติบุคคล
- โอนรถข้ามนิติบุคคล **ทำไม่ได้** ต้องเปิดบิลขายส่ง (B2B) เพราะต้องมีใบกำกับจริง
- เฟสของดีล 4 ขั้น: **คุยกับลูกค้า → ไฟแนนซ์ → เปิดการขาย → ส่งมอบ**
  เป็น "เลนส์" คำนวณจากระเบียนจริง **ไม่เก็บเป็นฟิลด์** (กันสถานะซ้ำซ้อน)

## 8. กับดักที่เสียเวลาไปแล้ว — อย่าเหยียบซ้ำ

**CSS / เบราว์เซอร์**
- `backdrop-blur` บน ancestor ทำให้ลูกที่ `position:fixed` ยึดกับ ancestor นั้นแทนหน้าจอ
  → ชั้นซ้อนที่เปิดจากแถบบน **ต้อง portal ไปที่ `<body>`** (`tests/modal-portal.test.ts` กันไว้แล้ว)
- CSS ของผู้ใช้ต้องชนะด้วย **specificity** (`html:root:root`) ไม่ใช่ลำดับใน DOM
  เพราะธีมของร้านถูกเรนเดอร์ทีหลังใน `<body>`
- `requestAnimationFrame` **ไม่ทำงานเลยถ้าแท็บถูกซ่อน** → รอ DOM ด้วย `setTimeout` ในงานที่ผู้ใช้กด
- `.print-doc` เป็น `display:none` บนจอ แคปเป็นภาพไม่ได้ ต้องเรนเดอร์อีกชุดนอกจอ
- Chrome CLI `--window-size` **ไม่มีผลกับ layout** ในโหมด headless ใหม่ — `--screenshot` ได้ภาพครอปของ layout 800px

**ฐานข้อมูล**
- RLS กันได้แค่ระดับ **แถว** ไม่ใช่ระดับคอลัมน์ · ผู้ใช้ที่ล็อกอินทุกคนเป็น role `authenticated` เดียวกัน
  → `revoke select (คอลัมน์)` ตัดสิทธิ์ทุกบทบาทพร้อมกัน ต้องเปิดทางกลับผ่านฟังก์ชันที่ตรวจสิทธิ์เอง
- **ห้ามใช้ view ปิดคอลัมน์ในสคีมา `public`** — `security_invoker` เปิดก็ติดสิทธิ์คอลัมน์ ปิดก็ข้าม RLS ของตารางแม่
- `app_setting.value` เป็น `jsonb` → ต้อง `to_jsonb('...'::text)`
- `pgcrypto` อยู่สคีมา `extensions` → `extensions.gen_random_bytes`

**เวิร์กโฟลว์**
- เทสต์บางตัวผูกข้ามไฟล์ (README ↔ โฟลเดอร์ migration · คู่มือ ↔ migration 08 · เมนู ↔ MobileNav)
  แก้ที่เดียวแล้วอีกที่แดง → **รันเทสต์เต็มชุดก่อน push เสมอ**
- แตกหลายสาขาพร้อมกันแล้วแตะไฟล์เดียวกัน → merge `origin/main` เข้าสาขาก่อน push
- เคยสรุปผิดเพราะ `grep` มองข้ามการเรียงฝั่ง client ที่อยู่หลัง `.filter()` — **ตรวจให้เห็นของจริงก่อนสรุป**

## 11. ถ้าจะเทียบกับเวอร์ชันของเพื่อน

**เทียบที่ "พฤติกรรมของระบบ" ก่อน อย่าเทียบที่โค้ด** — สองเวอร์ชันแก้โจทย์เดียวกันคนละวิธี
เทียบทีละเรื่องว่าใครจัดการยังไง แล้วค่อยดูว่าวิธีไหนเหมาะกับสิ่งที่ลูกค้าพูดในที่ประชุม:

1. สิทธิ์และการซ่อนตัวเงิน — กันที่ไหน (แอป / DB) · ยิง API ตรงแล้วรั่วไหม
2. การแยกข้อมูลระหว่างบริษัท — RLS ที่ DB หรือกรองในแอป
3. ขายรถพร้อมกันสองคน — กันขายซ้ำยังไง
4. เลขเอกสาร — กันซ้ำ/กันขาดช่วงยังไง ตอนยกเลิกทำอะไร
5. เอกสารภาษีขายผ่อน — ออกกี่ใบ ชื่อใคร
6. ปิดงวดเงินเดือน — แช่ยอดไหม หรือคำนวณใหม่ทุกครั้ง
7. ต้นทุนอะไหล่ — แช่ ณ เวลาเคลื่อนไหว หรืออ่านราคาปัจจุบัน (กระทบกำไรย้อนหลัง)
8. มือถือ — ออกแบบมาให้ใช้บนมือถือจริงไหม
9. เทสต์ — มีไหม ครอบอะไร

**สิ่งที่ควรระวังตอนหยิบแนวคิดข้ามเวอร์ชัน** (ย้ำ: หยิบ *แนวคิด* ไม่ใช่หยิบ *ไฟล์* — ดูข้อ 0.5)
- อย่ายกโค้ดที่แตะเงิน/สิทธิ์ข้ามมาโดยไม่ดูว่า RLS อีกฝั่งวางไว้ยังไง — ด่านอาจอยู่คนละที่
- `database.types.ts` ของรีโปนี้เขียนมือ เขียนโค้ดใหม่แล้วต้องมาเพิ่ม type เอง
- migration ของสองเวอร์ชันเป็นคนละชุด **ห้ามเอาไฟล์ migration ข้ามมาตรง ๆ**
- ถ้าจะยกอะไรมาจริง ๆ ให้เปิดตั๋วใหม่ในรีโปนี้ เขียนเองตามกติกาที่นี่ แล้วเทสต์เอง
