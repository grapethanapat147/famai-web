# FAM-1144 — ปิดสลิปเงินเดือนที่ระดับฐานข้อมูล (ส่วนแรกของ FAM-1141)

**สถานะ:** Done
**สาขา (git):** `feature/FAM-1144-payslip-rls`
**ต้องรัน SQL:** ใช่ — `supabase/migrations/20260904120000_39_payslip_money_rls.sql`

## ปัญหา
policy เดิมของตาราง `payslip` (migration 31) เขียนว่า "เห็นได้ถ้าเข้าถึงบริษัทของงวดนั้นได้"
ไม่ได้ดูสิทธิ์ `money` เลย → **พนักงานคนไหนก็ได้ที่เอา token ของตัวเองไปยิง PostgREST ตรง ๆ
อ่านเงินเดือน OT และคอมมิชชั่นของเพื่อนร่วมงานได้ทั้งบริษัท** การซ่อนบนหน้าจอกันได้แค่คนที่ใช้ผ่านแอป

หนักกว่านั้น: งวดที่ `branch_id` เป็น null (แปลว่า "ทุกบริษัท" — งวดในชุดข้อมูลตัวอย่างก็เป็นแบบนี้)
เงื่อนไขเดิมปล่อยผ่านทันที ข้อมูลจึงข้ามบริษัทได้ด้วย

## ทำอะไรบ้าง
**`has_money()`** — ฟังก์ชัน security definer อ่าน `role.perms->>'money'` ของผู้ใช้ปัจจุบัน
เขียนให้เข้าชุดกับ `is_admin()` / `is_all_branch()` / `my_branches()` ที่มีอยู่แล้ว

**เปลี่ยน policy ของ `payslip` เป็นสองชั้น**
- `payslip_manage` — ผู้มีสิทธิ์ตัวเงินจัดการได้ทั้งงวด ภายในบริษัทที่ตัวเองเข้าถึงได้ (เงื่อนไขเดิม + `has_money()`)
- `payslip_own` — ใครก็ตามอ่าน **สลิปของตัวเอง** ได้เสมอ (policy แบบ permissive หลายอันถูก OR กัน)
  เผื่อวันหน้าทำหน้าให้พนักงานเปิดสลิปตัวเอง จะไม่ต้องมาแก้สิทธิ์อีก

**ไม่ต้องแก้โค้ดแอปเลยแม้แต่บรรทัดเดียว** — หน้าเงินเดือนเปิดให้เฉพาะ admin / manager / hr / acct
ซึ่งทั้งสี่บทบาทมี `money = true` อยู่แล้ว (ดู `ROLE_PERMS` และ migration 08) จึงทำงานเหมือนเดิมทุกประการ

## เทสต์
เพิ่ม 3 เคสใน `tests/integration/security.test.ts` (รันเมื่อมี secret): เซลล์ยิงตรงต้องได้ลิสต์ว่าง ·
ผู้มีสิทธิ์ตัวเงินยังอ่านได้ (ไม่ได้ปิดจนใช้งานไม่ได้) · `has_money()` ตอบตรงกับสิทธิ์จริง

## ที่ยังเหลือ
`employee.base_salary` ยังอ่านได้อยู่ด้วย token ของใครก็ได้ — ปิดไม่ได้ด้วย RLS เพราะเป็น**คอลัมน์**ไม่ใช่แถว
ต้อง `revoke select (base_salary)` แล้วให้ 3 จุดที่อ่านมันไปเรียกผ่าน RPC แบบ security definer แทน
(หน้าพนักงาน · หน้าเงินเดือน · คำนวณสลิป) แยกเป็นตั๋วต่างหากเพราะแตะโค้ดแอปและต้องทดสอบกับฐานข้อมูลจริง

หมายเหตุสำคัญที่พบระหว่างทาง: แนวทางเดิมใน FAM-1141 ที่เขียนว่า "column-level GRANT ต่อ role"
**ทำไม่ได้บน Supabase** เพราะผู้ใช้ที่ล็อกอินทุกคนเป็น Postgres role เดียวกันคือ `authenticated`
(RLS ทั้ง 67 policy ผูกกับ role นี้) การ revoke สิทธิ์คอลัมน์จึงตัดของผู้บริหารไปพร้อมกัน
