# FAM-1141 — กันคอลัมน์ตัวเงินที่ระดับฐานข้อมูล (defense in depth)

**สถานะ:** Backlog
**สาขา (git):** ยังไม่เริ่ม
**ต้องรัน SQL:** ใช่ (migration ใหม่ เมื่อเริ่มทำ)
**Epic:** FAM-E02

> ยกเนื้อหามาจากสาขา `chore/security-hardening-ticket` ใน FAM-1140
> สาขานั้นแตกจาก main รุ่นเก่ามาก (merge ตรง ๆ จะลบตั๋วบนกระดานทิ้งกว่า 130 ใบ) จึงยกเฉพาะเนื้อตั๋วมา
> บนสาขานั้นตั๋วนี้ใช้เลข FAM-1021 ซึ่งชนกับ "หน้ารายงาน" ที่ main ใช้เลขเดียวกันไปแล้ว จึงให้เลขใหม่

## ปัญหา
การซ่อนตัวเงินตอนนี้อยู่ที่ **ชั้นแอปอย่างเดียว** (`lib/auth/strip-money.ts` · `stripMoneyFields`)
RLS ของ Supabase กันที่ระดับ **แถว** (แยกตามบริษัท) แต่ **ไม่กันระดับคอลัมน์**

ผู้ใช้ที่ไม่มีสิทธิ์ `money` (เช่น เซลล์ · สต๊อก · ช่าง) ถ้าเอา session token ไปยิง PostgREST
ของ Supabase **ตรง ๆ โดยไม่ผ่านแอป** จะอ่านคอลัมน์ต้นทุน/กำไรได้ ทั้งที่หน้าจอซ่อนไว้แล้ว

## คอลัมน์ที่ต้องกัน
- `motorcycle_unit.cost` · `cost_vat`
- `sale.cost` · `gross_profit` · `freebie_cost`
- `wholesale_order_line.cost`
- `part.cost` · `part_movement.unit_cost` (เพิ่มใน FAM-1137)
- `receivable.amount_due` · `amount_paid` · `finance_case.amount`
- `employee.base_salary` · ทุกคอลัมน์ใน `payslip`

## แนวทาง (เลือกหรือผสม)
1. **view ที่ตัดคอลัมน์เงินออก** แล้ว revoke SELECT คอลัมน์เงินบนตารางจริงสำหรับ role ที่ไม่มีสิทธิ์
   (รูปแบบเดียวกับสคีมา `pub` ใน `docs/07-public-api.md`)
2. **column-level GRANT** ต่อ role
3. ไม่ว่าทางไหน ฐานข้อมูลต้องรู้สิทธิ์ `money` ของผู้ใช้ → helper `has_money()` แบบ security definer
   ที่อ่าน `role.perms->>'money'` (ทำแบบเดียวกับ `is_admin()` / `is_all_branch()` ที่มีอยู่แล้ว)

## เกณฑ์ว่าเสร็จ
- ผู้ใช้ที่ไม่มีสิทธิ์ `money` ยิง PostgREST ตรง → response **ไม่มี** คอลัมน์เงินของตารางข้างบน
- ผู้ใช้ที่มีสิทธิ์ยังอ่านได้ปกติ · การแยกข้อมูลตามบริษัท (RLS เดิม) ไม่พัง
- migration ใหม่ ไม่แก้ไฟล์เดิมที่รันไปแล้ว
- ต่อยอด `tests/integration/security.test.ts`: ล็อกอินเป็นเซลล์ → query ตารางเงินตรง → ยืนยันว่าไม่มีคอลัมน์เงิน
  (`RUN_INTEGRATION=1 npx vitest run tests/integration`)

## อัปเดต (FAM-1144)
- **แนวทางที่ 2 (column-level GRANT ต่อ role) ทำไม่ได้บน Supabase** — ผู้ใช้ที่ล็อกอินทุกคนเป็น
  Postgres role เดียวกันคือ `authenticated` (RLS ทั้ง 67 policy ผูกกับ role นี้) revoke แล้วตัดของทุกคนพร้อมกัน
  เหลือทางเดียวคือแนวทางที่ 1 (view / RPC ที่ปิดคอลัมน์ด้วย `has_money()`)
- **ส่วนสลิปเงินเดือนทำไปแล้วใน FAM-1144** — `has_money()` มีแล้ว และ `payslip` รัดสิทธิ์แล้ว
  ตั๋วนี้จึงเหลือตารางอื่น: `employee.base_salary` · `motorcycle_unit` · `sale` · `receivable` ·
  `finance_case` · `part` · `part_movement` · `wholesale_order_line`
- ขนาดงานที่วัดไว้: `base_salary` 3 จุดที่อ่าน · กลุ่มกลาง ~12 จุด · `motorcycle_unit`+`sale` 30+ จุด

## อัปเดต (5 ก.ย. 2569 — ขอบเขต "เงินเดือน" ปิดครบแล้ว)
- FAM-1144: `payslip` รัดสิทธิ์ด้วย `has_money()` แล้ว — เจ้าของรัน SQL แล้ว
- FAM-1145: `employee.base_salary` · `ssn_no` · `bank_code` · `bank_account` ถูก `revoke select`
  อ่านได้ทางเดียวผ่าน `employee_pay_info()` — เจ้าของรัน SQL และเปิดหน้าจอยืนยันแล้วว่าตัวเลขขึ้นครบ
- **เหลือกลุ่มต้นทุน/กำไร**: `motorcycle_unit.cost/cost_vat` · `sale.cost/gross_profit/freebie_cost` ·
  `receivable` · `finance_case.amount` · `part.cost` · `part_movement.unit_cost` · `wholesale_order_line.cost`
  วิธีทำเหมือนกันทุกประการกับ FAM-1145 (revoke คอลัมน์ + ฟังก์ชัน security definer) แต่จุดที่ต้องแก้เยอะกว่ามาก

## หมายเหตุ
- การซ่อนที่ชั้นแอป (FAM-1006) **ยังคงไว้** — ตั๋วนี้เพิ่มชั้นฐานข้อมูล ไม่ใช่แทนที่
- เงื่อนไขเดิมที่ว่า "ต้องรอผลตัดสิน บริษัท vs สาขา" **หมดไปแล้ว** — ตัดสินใน FAM-1111/FAM-1129
  ("บริษัท" ใน UI = `branch` · ข้ามนิติบุคคลใช้ขายส่ง) เริ่มทำได้เลย
- ทำก่อนเปิดให้พนักงานใช้จริงหลายคนจะคุ้มที่สุด เพราะเป็นการเปลี่ยนสิทธิ์ระดับฐานข้อมูล
