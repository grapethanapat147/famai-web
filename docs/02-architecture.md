**หลักการเดียวที่สำคัญที่สุด: แยกข้อมูลรายสาขาที่ระดับฐานข้อมูล ไม่ใช่ที่หน้าเว็บ**

ใน v0.5 สิทธิ์ `allBranch` เป็นแค่ checkbox ที่ไม่มีโค้ดอ่านค่า — UI พลาดเมื่อไหร่ข้อมูลรั่วทันที
ระบบใหม่ใช้ **Row Level Security ของ PostgreSQL** ซึ่งบังคับที่ฐานข้อมูล
ต่อให้เขียนหน้าเว็บผิด หรือมีคนยิง API ตรง ๆ ข้อมูลสาขาอื่นก็ยังออกมาไม่ได้

## 2. ทำไมเลือกชุดนี้

| เทียบกับทางเลือกอื่น | ข้อสรุป |
|---|---|
| **VPS เดียว + Docker + Postgres** | ถูกกว่าเดือนละไม่กี่ร้อยบาท แต่ต้องอัปเดตความปลอดภัยเอง ต่อ SSL เอง สำรองข้อมูลเอง เซิร์ฟเวอร์ล่มตอนตีสองต้องมีคนแก้ — **ไม่ตรงเงื่อนไข "ดูแลง่าย"** |
| **Google Sheets / Excel ออนไลน์** | ฟรี แต่ไม่มีสิทธิ์รายสาขา ไม่มีเลขเอกสารกันซ้ำ ไม่มี audit log และพังเมื่อข้อมูลโต |
| **ซื้อ ERP สำเร็จรูป** | เร็วกว่าตอนเริ่ม แต่ค่ารายเดือนต่อผู้ใช้แพงกว่า ปรับให้ตรงงานร้านไม่ได้ และผูกกับผู้ขาย |
| **Firebase** | ใช้ได้ แต่เป็น NoSQL — ระบบนี้มีความสัมพันธ์เยอะ (รถ ↔ ขาย ↔ ทะเบียน ↔ ไฟแนนซ์ ↔ service) และต้องทำรายงานสรุป SQL เหมาะกว่ามาก |
| **Neon + Vercel Blob** | มีแพ็กฟรี แต่ **Neon Free รัน cron ไม่ได้จริง** (พับ compute 5 นาที ปิดไม่ได้ งานตอนเช้าจึงไม่ทำงาน) · ไม่มี Auth ให้ · ย้ายกลับมา Supabase ทีหลัง ~31–64 ชม. (ดู §3) |
| **Cloudflare Pages** | ฟรี ไม่ห้ามเชิงพาณิชย์ — เก็บไว้เป็น**ทางสำรอง**ถ้าวันหนึ่งเลิก Vercel Pro |
| **✅ Next.js บน Vercel Pro + Supabase** | SQL แท้ · RLS แยกสาขาให้ในตัว · Auth/Storage มาพร้อม · SSR เต็มรูปแบบ · Vercel Cron ฟรี · Vercel Pro จ่ายอยู่แล้วจึงเป็น ฿0 ส่วนเพิ่ม · ย้ายออกได้เพราะเป็น Postgres มาตรฐาน |

**ข้อดีที่ไม่ค่อยมีใครพูดถึง:** Supabase คือ PostgreSQL ธรรมดา
ถ้าวันหนึ่งอยากย้ายไปเซิร์ฟเวอร์ตัวเอง แค่ `pg_dump` แล้วย้าย — **ไม่ผูกขาด**

ทางสำรองคือ **Cloudflare Pages** — ฟรี ไม่จำกัด ไม่ห้ามใช้เชิงพาณิชย์

**สิ่งที่ไม่เปลี่ยนไม่ว่าจะโฮสต์ที่ไหน:** RLS แยกสาขาระดับฐานข้อมูล · เลขเอกสารกันซ้ำด้วย

### LINE ไม่ได้ฟรีแบบไม่จำกัด

เอกสารรุ่นก่อนลง LINE ไว้ ฿0 ซึ่งทำให้เข้าใจผิด — **โควตาฟรีคือ 300 ข้อความ/เดือน**

| แพ็ก | ต่อเดือน | ข้อความที่รวม | ส่วนเกิน |
|---|---|---|---|
| Free | ฿0 | **300** | — |
| Basic | ฿1,369.60 (รวม VAT) | 15,000 | ฿0.10/ข้อความ |
| Pro | ฿1,904.60 (รวม VAT) | 35,000 | ฿0.06/ข้อความ |

นับตาม **จำนวนผู้รับ** — push, multicast, broadcast นับหมด · **ข้อความตอบกลับ (reply) ไม่นับ**

แผนแจ้งเตือนใน §7 (เตือนเช็กระยะ 4 ระยะ · ทะเบียนออก · พ.ร.บ. ใกล้หมด · สรุปยอดรายวัน)
แค่ขายเดือนละ 50 คัน 3 สาขา เฉพาะเตือนเช็กระยะก็ ~200 ข้อความ/เดือนแล้ว

**ออกแบบให้ประหยัดโควตา — ทำตั้งแต่วันแรก**
1. แจ้งเตือนพนักงานส่งเข้า **กลุ่ม LINE** ไม่ใช่รายคน (สรุปยอดรายวัน เตือนรถค้าง เตือนเคสสินเชื่อ)
2. **รวมหลายเรื่องเป็นข้อความเดียว** — "รถของคุณ 3 คันพร้อมรับ" ดีกว่าส่ง 3 ข้อความ
3. ใช้ **rich menu** ให้ลูกค้ากดดูสถานะเอง — ข้อความตอบกลับไม่กินโควตา
4. ขึ้น Basic เมื่อจำเป็นจริง แล้วค่อยบวกเข้างบ

## 4. เรื่องที่ Postgres แก้ให้ได้เลยโดยแทบไม่ต้องเขียนโค้ด

### 4.1 เลขที่เอกสารไม่มีวันซ้ำ

ปัญหาใหญ่สุดของ v0.5 (`RC-` + จำนวนแถว) แก้ได้ด้วยตารางตัวนับ + ล็อกแถว:

```sql
create table doc_counter (
  branch_id  uuid    not null references branch(id),
  doc_type   text    not null,          -- 'RECEIPT' | 'TAX_INV' | 'QUOTE' | ...
  year_be    int     not null,          -- ปี พ.ศ.
  last_no    bigint  not null default 0,
  primary key (branch_id, doc_type, year_be)
);

create function next_doc_no(p_branch uuid, p_type text, p_year int)
returns text language plpgsql as $$
declare n bigint; pfx text;
begin
  insert into doc_counter(branch_id, doc_type, year_be, last_no)
  values (p_branch, p_type, p_year, 0)
  on conflict do nothing;

  update doc_counter set last_no = last_no + 1
   where branch_id = p_branch and doc_type = p_type and year_be = p_year
  returning last_no into n;                 -- ล็อกแถวอัตโนมัติ ออกพร้อมกันก็ไม่ชน

  select doc_prefix into pfx from branch where id = p_branch;
  return pfx || '-' || p_type || '-' || p_year || '-' || lpad(n::text, 5, '0');
end $$;
```

ได้เลขแบบ `FMG-TAX_INV-2569-00042` — **แยกสาขา แยกประเภท แยกปี ไม่ซ้ำแม้ออกพร้อมกัน**

### 4.2 แยกข้อมูลรายสาขา (RLS)

```sql
alter table sale enable row level security;      -- ลืมบรรทัดนี้ = policy ไม่มีผลบังคับ

create policy sale_branch_scope on sale
for all to authenticated
using      (is_all_branch() or branch_id in (select my_branches()))
with check (is_all_branch() or branch_id in (select my_branches()));
```

`my_branches()` / `is_all_branch()` เป็นฟังก์ชัน `security definer` ที่อ่านจาก `app_user_branch`
และ `app_user.all_branch` — แยกออกมาเพื่อไม่ต้องเขียน subquery ซ้ำ 20 ตาราง
(ดูตัวจริงที่ `supabase/migrations/20260803231705_05_functions_and_audit.sql`)

เขียนครั้งเดียวต่อตาราง — **ใช้กับทุกหน้าจอ ทุก API โดยอัตโนมัติ**

ข้อควรระวังที่เจอตอนลงจริง 3 ข้อ
- ตารางที่ `branch_id` เป็น `null` ได้ (เช่น `promotion` null = ทุกสาขา) ต้องเขียน
  `branch_id is null or ...` ไม่งั้น `null in (...)` ได้ค่า NULL แถวจะหายไปจากทุกคน
- 5 ตารางที่ไม่มี `branch_id` เลย (`receipt_payment` `attendance` `leave_request`
  `payroll_line` `attachment`) ต้องเขียนแบบ `exists (select 1 from <ตารางแม่> ...)`
- ห้ามถอน `execute` ของฟังก์ชันช่วยออกจาก role `authenticated` — policy ถูกประเมิน
  ในสิทธิ์ของผู้เรียก ถอนแล้วจะได้ `permission denied for function my_branches`

### 4.3 Audit log

```sql
create table audit_log (
  id bigserial primary key,
  at timestamptz not null default now(),
  actor uuid, table_name text, row_id text,
  action text, before jsonb, after jsonb
);
-- ผูก trigger เดียวใช้กับทุกตารางที่ต้องการ
```

ตอบได้ทันทีว่า *ใครแก้ราคาคันนี้ เมื่อไหร่ จากเท่าไหร่เป็นเท่าไหร่*

### 4.4 งานอัตโนมัติ (Vercel Cron)

| เวลาไทย | cron (UTC) | งาน |
|---|---|---|
| ทุกวัน 06:00 | `0 23 * * *` | สร้างงานติดตาม 7/30/90 วัน/1 ปี/3 ปี ที่ถึงกำหนด |
| ทุกวัน 06:05 | `5 23 * * *` | หารถที่รอทะเบียนเกินเกณฑ์ → แจ้ง LINE |
| ทุกวัน 06:10 | `10 23 * * *` | หาสต๊อกค้างเกิน 90 วัน → สรุปส่งผู้จัดการ |
| ทุกวัน 08:00 | `0 1 * * *` | ลูกค้าที่ถึงรอบเช็กระยะ → รายการส่ง LINE |
| ทุกวันที่ 25 | `0 1 25 * *` | เตือนปิดเงินเดือน |

**ใช้ Vercel Cron ไม่ใช่ pg_cron** — แพ็ก Pro ให้ 100 งานต่อโปรเจกต์ ความละเอียดระดับนาที ฟรี
แต่ละงานเป็น API route ธรรมดา ป้องกันด้วย `CRON_SECRET` ใน header

ดีกว่า pg_cron ตรงที่ **เห็น log ได้ · ทดสอบได้ · อยู่ใน Git** และตัดเงื่อนไข
"ฐานข้อมูลต้องตื่นตลอดเวลา" ทิ้ง ทำให้ย้ายผู้ให้บริการฐานข้อมูลทีหลังถูกลงทุกทาง

> ⚠️ cron ของ Vercel ตั้งเป็น **UTC** — เวลาไทยเร็วกว่า 7 ชั่วโมง 06:00 น. ไทยจึงเป็น `0 23 * * *`
> ของวันก่อนหน้า ต้องระวังตอนคำนวณ "เมื่อวาน" ในตัวงานเอง

## 9. e-Tax Invoice — ตัดสินใจแล้วว่าจะใช้

คุณเลือก **ใบกำกับภาษีอิเล็กทรอนิกส์** แทนกระดาษ ซึ่งกระทบการออกแบบตั้งแต่ต้น จึงต้องวางไว้ใน Phase 1

### สิ่งที่ต้องมี

| รายการ | รายละเอียด |
|---|---|
| **ใบรับรองอิเล็กทรอนิกส์ (CA)** | ออกโดยผู้ให้บริการที่สรรพากรรับรอง ใช้ลงลายมือชื่อดิจิทัลบนเอกสาร · มีค่าธรรมเนียมรายปี |
| **ผู้ให้บริการ (Service Provider)** | ตัวกลางที่ลงลายมือชื่อและนำส่งข้อมูลให้สรรพากร — คิดค่าบริการรายเดือนหรือรายฉบับ |
| **รูปแบบเอกสาร** | XML ตามมาตรฐาน ETDA + PDF/A-3 ที่ฝัง XML ไว้ข้างใน สำหรับส่งลูกค้า |
| **การนำส่ง** | ส่งข้อมูลให้สรรพากรตามรอบที่กำหนด |
| **การเก็บรักษา** | เก็บไฟล์ต้นฉบับพร้อมลายมือชื่อไว้ตามอายุที่กฎหมายกำหนด |

### ผลต่อสถาปัตยกรรม

- ตาราง `document` ต้องเพิ่ม `xml_payload` · `signed_at` · `submit_status` · `provider_ref`
- ต้องมีคิวส่งเอกสาร (retry ได้) เพราะ API ของผู้ให้บริการอาจล่ม
- **เลขที่เอกสารห้ามซ้ำและห้ามข้ามเด็ดขาด** — ตัวนับใน §4.1 ตอบโจทย์นี้อยู่แล้ว
- ยกเลิกเอกสารต้องออก **ใบลดหนี้** ไม่ใช่ลบทิ้ง → `document.voided_at` มีอยู่แล้ว แต่ต้องเพิ่มเอกสารคู่
- ต้องเก็บ log การนำส่งทุกฉบับไว้ตรวจสอบย้อนหลัง

### ค่าใช้จ่ายเพิ่ม

ขึ้นกับผู้ให้บริการและปริมาณเอกสาร — **ต้องขอใบเสนอราคาจากผู้ให้บริการ 2–3 ราย**
โดยแจ้งปริมาณจริง (จำนวนใบกำกับภาษีต่อเดือน × 3 สาขา) ก่อนตัดสินใจ

> 💡 **แนะนำ:** คุยกับผู้ทำบัญชีของร้านก่อน เพราะบางสำนักงานบัญชีมีผู้ให้บริการที่ใช้อยู่แล้ว
> และช่วยลดงานตรวจสอบได้มาก
